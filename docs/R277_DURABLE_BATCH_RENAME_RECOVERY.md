# R277 — Durable, user-approved recovery after interrupted Batch Rename

The earlier R275 Apply/Undo could roll back errors **inside the running process**, but there was no durable evidence after a hard crash or power loss. R277 adds a local, per-folder, write-ahead recovery journal under `%LOCALAPPDATA%\DeskSpace\BatchRename\Recovery\<SHA-256 folder key>.json`. It contains only the chosen folder, planned before/after names, file lengths and last-modified timestamps; **no file contents** or network activity. The record is written to an adjacent unique file using a write-through file stream, flushed to storage, then atomically renamed to its canonical path **before the first batch rename**.

The Batch Rename UI uses the journal-backed Apply and Undo entry points and adds **Review previous batch** and **Recover reviewed batch**. The latter requires a fresh folder selection, displays how many names are still changed and exactly which changes would be undone, rechecks the folder, and asks explicit confirmation. There is **no automatic recovery or background file movement on startup**. The user can close the window; the local record persists, and it can be reviewed after restarting.

Recovery checks each recorded original/destination pair and only accepts either (1) a matching original with absent destination (no action) or (2) a matching renamed file with absent original (eligible to undo). If both, neither, an altered file, malformed/tampered journal, linked/system folder, inconsistent names, or occupied target exists, recovery refuses to move anything. The existing R275 per-folder OS mutex, metadata checks and `File.Move(...,overwrite:false)` apply to the actual file restoration. A mixed partial operation is recoverable: only files still renamed are undone, untouched originals are left alone. A successful recovery clears the journal; errors keep it for later review.

**Windows regression:** Tests create real files in a disposable test folder, Apply and inspect a persisted record, verify mere inspection never moves data, undo after a simulated process restart, undo an intentionally half-complete transaction, block collisions, clear a pre-move journal only after explicit consent, and reject malformed JSON without modifying files. Full WPF build, static safety checks, deterministic patched-source reconstruction and canonical source integrity are mandatory before development acceptance.

**Limitations:** a malicious external program with write access to the same user journal might alter it (name validation and metadata guards still prevent path traversal/overwrite). This mechanism is for regular local filesystem renames; actual power-cut/antivirus/network-share acceptance and externally edited files remain device-only tests. Do not ship to Stable or Tester until the consolidated release gate and installed-PC acceptance are complete.
