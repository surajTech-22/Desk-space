# R276 — major startup/tray recovery: early widget constructor failure

The preexisting R183 crash-loop guard was called by the widget's **Loaded** handler. If construction or initial `Show()` failed, there was no startup marker, no graceful app entry point, and sometimes no visible tray. R276 records the short-start marker **immediately after acquiring the widget-host single-instance mutex**, before creating `WidgetShellWindow`. The normal Loaded handler now attaches the 45-second stability timer without duplicating the recorded startup session. Clean process exits mark healthy only if the widget successfully loaded and armed its tracker. This improves the R183 three-short-failure safe-mode behavior and preserves normal startup if its marker file is inaccessible.

For expected WPF/IO/Win32 constructor failures, the app shows a minimal, non-duplicating recovery **window + tray icon**. It reports only the exception type (not private paths/data), offers explicit Open Workspace and Close controls, and never reads or edits user documents, settings or Excel mappings. The fallback does not automatically restart the failed widget or reinitialize secondary monitors; a user can still access Workspace and Component Status. All other unrecoverable exceptions retain normal failure behavior rather than being disguised as success.

The recovery marker continues to live in the existing `%LOCALAPPDATA%\DeskSpace\Recovery\startup-v1.json`. The app retains the original single-instance mutex and named pipe for successful normal widgets. Native WPF tests instantiate and inspect the real recovery dialog, confirm that its controls are explicit, and assert early marker and clean-exit entry points. Static validation verifies the critical order (record before construction) and forbids workspace access in the fallback. Physical bad-install, Explorer-restart and two-display startup acceptance are **not** covered by CI, so Stable/Tester release remains blocked.
