# R286 — Tray Exit Widget must stay exited until Show Widget

**Reported:** When users choose **Exit widget** from DeskSpace's tray, the widget reappears without a further Show Widget command. The primary cause was that the tray called `Close()` but saved no explicit user intent. The Workspace constructor still called `ShowFloatingWidget` on startup (which uses `EnsureRunning(force:true)`), and the Windows `Run` entry launches `--widget-host` directly. Either route can relaunch the widget even after a user exited it.

**Implemented:** A private, minimal `widget-user-exited-v286.flag` file in DeskSpace's existing LocalAppData workspace. The tray's **Exit widget** handler saves it atomically before calling the usual (non-forced) WPF close. If the write fails, it leaves the widget open and explains why rather than causing surprise reopening. The automatic Workspace `ShowAtLaunch` path now calls `EnsureRunning(false)`; the normal widget launcher refuses automatic starts while the flag exists. The App startup `--widget-host` path likewise exits immediately on a saved explicit Exit, so the Windows startup registry and automatic updater relaunch cannot override the user. Only deliberate **Show Widget** actions (`EnsureRunning(true)` from Workspace button, main tray, explicit Search/Excel commands) clear the marker before launching/revealing the widget.

**Unchanged:** Start-with-Windows and ShowAtLaunch preferences remain as configured; user settings, all held files, Excel mappings, monitor offsets and saved apps are untouched. Multi-monitor satellites close with the primary widget as before. No polling daemon or process kill. The next explicit Show can start the full monitor widgets again. No browser/network access or private data read is required.

**Testing:** CI includes a native Windows filesystem-backed sticky Exit/Show test covering automatic startup, repeated Exit, repeated Show, and readback after persisted marker; static gates ensure the real tray handler, App startup and Workspace startup all consult the same marker. The full R201–R286 WPF suite, synthetic installer rollback, canonical source parity and independent build must pass.

**Limitations:** CI does not prove installed updater behavior or physical dual-monitor state. The user requested a consolidated update, but the repository's P0 release gates for a real installed updater, Excel Office test workbooks, physical dual-monitor and Authenticode signing still require verified evidence before a production Stable/Tester update can be claimed.
